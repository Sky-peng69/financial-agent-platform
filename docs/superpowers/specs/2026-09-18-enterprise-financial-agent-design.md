# 弈金企业金融动态尽调与决策智能体设计

日期：2026-09-18
状态：设计稿，待用户评审

## 1. 设计结论

弈金不再以“上市公司研究报告生成器”作为产品中心，也不以 Agent 数量作为差异化。

新的产品定位是：

> 弈金是一套面向银行公司金融、普惠金融和风险管理场景的企业金融动态尽调与决策智能体，持续感知企业经营变化，融合公开资料、企业材料和授权业务数据，生成可验证的企业画像、风险判断和金融行动建议。

一句话价值主张：

> 让每一次企业变化，都转化为可解释的金融行动。

上市公司研究保留为数据理解和企业分析能力的一部分，不再作为产品叙事的终点。

## 2. 设计依据

本设计参考四个第十六届工行杯获奖案例视频：

- `16th1.mp4`：新农小精通，强调金融嵌入农村生产周期、线上线下服务和多类主体适配。
- `16届获奖案例2.mp4`：稀土如金，强调产业链数据、溯源、结算、融资、回收和国家战略闭环。
- `16th5.mp4`：一进调，强调银行员工尽调流程、多源数据、行业知识、风险提示、人工确认和落地集成。
- `16th6.mp4`：一起融，强调小微企业全景画像、动态额度、贷前贷中贷后风控和银行收益。

四个案例共同显示，金融科技项目的核心竞争力不是“有 AI”，而是把产业问题、银行业务、数据、金融产品、风险控制、工行价值和实施路径连成闭环。

## 3. 用户与核心任务

### 3.1 首要用户

- 银行公司金融/普惠金融客户经理
- 授信调查员和风险审查人员
- 行业金融团队和贷后管理人员

### 3.2 次要用户

- 企业财务负责人或融资负责人
- 银行产品经理
- 产业链和地方金融服务人员

### 3.3 核心任务

当客户经理面对一家信息不完整、经营变化快的企业时，系统帮助其完成：

```text
快速理解企业
  → 发现经营、财务和行业风险
  → 找到需要补充的证据
  → 判断企业真实金融需求
  → 形成可解释的金融行动建议
  → 人工复核并留下审计记录
  → 持续跟踪企业变化
```

## 4. 产品全链路

```text
企业授权接入
  → 材料和数据采集
  → 企业金融数字画像
  → AI 尽调与证据核验
  → 风险、机会和融资需求识别
  → 产品/授信/监控动作建议
  → 人工审批与业务确认
  → 服务执行与贷后监测
  → 结果反馈和画像更新
```

### 4.1 企业接入

MVP 支持上传 PDF、合同、订单、财报、资质和经营说明。后续通过授权连接器接入税务、电商、物流、银行流水和设备数据。

系统必须显示数据来源、授权范围、获取时间和当前可用性。

### 4.2 企业金融数字画像

画像不是单一信用分，而是结构化回答：

- 企业做什么，靠谁赚钱；
- 收入、客户、供应商和现金流是否集中；
- 订单、合同、发票和报表是否相互支持；
- 企业处于什么行业阶段和经营周期；
- 当前最可能的融资或金融服务需求是什么；
- 哪些判断仍缺少可靠证据。

### 4.3 AI 尽调

系统从企业材料和公开信息中提取事实，建立风险假设，并对每条关键判断绑定证据、反方证据、缺口和复核状态。

### 4.4 金融行动建议

系统只提出建议，不自动完成授信、调额、付款或交易。建议可以包括：

- 补充核验某项材料；
- 维持或重新评估授信；
- 设置订单、回款或账户行为监控；
- 匹配供应链金融、结算、绿色金融等产品；
- 安排客户经理沟通；
- 暂缓自动化流程并升级人工审查。

## 5. 核心产品对象

```text
Enterprise              企业主体
Evidence                证据项
BusinessEvent           企业/行业事件
FinancialState          企业金融状态
RiskHypothesis          风险或经营判断
FinancingNeed           金融需求
ActionRecommendation    金融行动建议
MonitoringRule          持续监测规则
ReviewAction            人工确认、驳回、编辑和审批记录
Outcome                 后续结果与复盘记录
```

现有对象的迁移关系：

| 当前对象 | 新产品对象 |
| --- | --- |
| ResearchSubject | Enterprise |
| Claim | RiskHypothesis / BusinessClaim |
| Assumption | CreditAssumption |
| DocumentEvidence | Evidence |
| Challenge | CounterEvidence |
| DecisionMemo | DueDiligenceMemo / CreditActionMemo |
| Commander | FinancialWorkflowOrchestrator |
| Report | 审计备忘录和业务工作包 |

## 6. Agent 架构

不按“行业分析、估值、消息面”继续扩展 Agent，而按金融流程职责划分：

1. 事实核验 Agent：抽取主体、金额、日期、合同条件和经营事实，并标注来源。
2. 企业画像 Agent：理解商业模式、客户/供应商依赖、经营周期和成长阶段。
3. 行业尽调 Agent：将企业放进行业周期、产业链和竞争环境中判断。
4. 风险与信用 Agent：识别经营、财务、欺诈、合同、合规和贷后风险。
5. 金融匹配 Agent：把企业需求匹配到结算、授信、供应链金融、绿色金融等行动。
6. 治理与审计 Agent：检查权限、证据、模型解释、人工复核和操作记录。

Agent 通过结构化协议交接，禁止下游只依赖隐式上下文。大模型负责理解、归纳和提出问题；金额计算、阈值判断、权限和最终审批必须由确定性规则与人工边界控制。

## 7. 系统架构

```text
数据接入层：企业材料、公开信息、授权业务数据
        ↓
证据层：解析、抽取、去重、定位、来源和授权记录
        ↓
企业金融状态层：企业、事件、现金流、合同、风险和需求关系
        ↓
Agent 工作流层：尽调、风险、需求、产品匹配和贷后监测
        ↓
治理控制层：策略、权限、审批、人工复核、回滚和审计
        ↓
业务输出层：尽调工作包、行动建议、监控任务和管理看板
```

保留现有 LLM Provider 与 Search Provider 抽象。Agent、编排层和报告层不得直接依赖具体模型 SDK。首版仍以用户材料和公开信息为主要数据来源，不把结构化金融数据接口写成已经接入的现状。

## 8. MVP 范围

第一阶段只做“企业金融尽调智能体”，证明以下闭环：

```text
上传企业材料
  → 建立企业画像
  → 识别风险与融资需求
  → 提供证据、反方和待核验项
  → 生成尽调工作清单与金融行动建议
  → 人工确认/驳回/编辑
  → 生成可审计备忘录
```

### MVP 必须具备

- PDF 上传、解析、页码级引用和权限隔离；
- 企业画像中的关键事实和来源；
- 至少一种行业场景的风险假设和金融需求识别；
- 关键判断的证据、反方、缺口和核验状态；
- 行动建议及其理由，不直接执行金融动作；
- 人工确认、驳回、编辑和不可变审计历史；
- 新事件输入后，明确标记受到影响的判断和建议；
- 在线展示和 PDF/Markdown 尽调备忘录导出。

### MVP 明确不做

- 自动授信审批和真实额度调整；
- 自动支付、交易或对外发送金融结论；
- 银行核心系统、税务、电商和流水接口的真实生产接入；
- 全行业覆盖和复杂组织权限；
- 面向普通投资者的个性化买卖建议；
- 把模型评分直接作为正式信用结论。

## 9. 竞赛演示脚本

选择“表面优质、实际存在客户集中和现金流风险的汽车零部件供应商”作为主案例。

```text
1. 上传企业材料，系统展示企业基本画像。
2. 系统发现订单、客户集中度、应收账款和利润现金流之间的矛盾。
3. 点击风险点，回链原始页码、合同条款和缺失证据。
4. Agent 提出补充核验问题和三种金融行动方案。
5. 输入“核心客户订单减少 30%”的新事件。
6. 系统展示受影响的判断、风险等级和行动建议变化。
7. 人工确认“分阶段额度 + 回款监控”方案，形成审计记录。
8. 展示银行、企业和实体经济三方价值。
```

演示重点不是生成长报告，而是展示“企业变化 → 判断变化 → 金融行动变化”的闭环。

## 10. 成功标准

- 用户能在一个企业对象内完成材料、判断、证据、建议和复核，不再产生孤立报告任务。
- 每条关键判断都能回到 PDF 页码、网页来源或明确的“待核验”状态。
- 新事件能通过结构化关系影响相关判断、风险和建议。
- 系统不会在缺少证据时猜测企业事实或财务数字。
- 金融行动建议必须显示依据、假设、风险和人工审批边界。
- 用户刷新或断线后仍能恢复企业状态、任务进度和审计历史。
- 相关测试覆盖文件解析、引用、事件更新、人工复核、权限和导出一致性。

## 11. 主要风险与边界

- 数据接入不足时，系统必须明确区分“已知、推测、待核验”。
- 行业规则不能被模型记忆替代，必须通过可版本化知识和人工复核管理。
- 建议与正式授信结论必须有清晰边界。
- 生产环境必须使用机构级身份、权限、密钥和审计机制。
- 当前竞赛材料不能把“适配工行方向”表述为已经获得工行授权、接入工行系统或完成商业合作。

## 12. 后续顺序

1. 用户评审并确认本设计稿。
2. 以现有 ResearchSubject 和证据链为基础，建立 Enterprise 金融尽调页面。
3. 将旧 Commander 输出改为结构化风险假设、证据缺口和行动建议。
4. 加入新事件影响分析和人工复核闭环。
5. 构造一组可复现的企业尽调评测集。
6. 再考虑动态现金流、授权数据连接器和贷后监测。
